# 浮游动物一体化：产品与工程优化方案（2026-07-27）

本方案基于当前已经具备的数据集、现场录入、AI、图片识别、导出、语音助手与 GitHub 更新能力。重点不是继续堆入口，而是让高频现场操作更少出错、长周期数据更可追溯、复杂能力在需要时才出现。

## 一、最值得优先解决的真实问题

### P0：现场录入时“我正在改什么、是否已经保存”不够明确

现状是采样点、物种、专注录入、全局助手和保存反馈分散在多个页面。重度使用时最危险的不是缺少功能，而是误以为当前点位/数据集已经切换或修改已经落盘。

方案：

1. 在物种页、专注录入和批量应用预览顶部统一放置一条不可折叠的工作会话栏：`数据集名称 · 当前点位 · 最近保存时间/保存中 · 未完成后台任务 · 撤销/重做`。
2. 点位切换、退出专注录入、导入覆盖和清空前都显示影响范围；当存在未完成 AI 任务或未保存编辑时，明确提示“继续后会怎样”。
3. 录入动作统一走事务编辑队列：快速 `+1` 合并为一条撤销记录，手动计数确认后一次写入，后台保存防抖但页面离开时强制落盘。

验收：连续录入 30 分钟后，用户无需回忆即可指出当前数据集、点位、最后一次成功保存和可撤销步数。

### P0：跨设备交接已能备份，但缺少“迁移成功”的确认闭环

本轮已经加入多选/全部数据集一键打包分享和一键导入。下一步不应再增加新格式，而应增强迁移验证。

方案：

1. 导出文件名写入数据集数量、日期、是否加密；导出页显示将打包的点位/物种总数。
2. 导入前预览按数据集列出：名称、点位数、物种数、更新时间、同名冲突数；默认“新增副本”，只有用户明确勾选才合并/覆盖。
3. 导入完成后展示导入前后数据集数量、失败项和可打开的诊断报告；不要只显示“导入成功”。
4. 为多个数据集打包建立一份可自动回归的样本，覆盖只读快照、别名、湿重库与加密包。

验收：两台设备之间迁移 20 个数据集后，用户能在导入结果页核对数量、冲突和数据完整性。

### P0：正式发布链路需从“能构建”变成“可持续交付”

正式签名、GitHub Release、应用内更新检查和 CI 已进入项目。接下来需要把签名、标签、发布说明、APK 校验变成固定门禁。

方案：

1. 每次发布使用 `v<versionName>` Git tag、固定 Release 说明、正式签名 APK、SHA-256 和证书指纹。
2. 应用内更新页显示：当前版本、最新版本、发布日期、包大小、更新说明、签名指纹是否与当前安装来源一致。签名不一致时只允许下载，不提示“覆盖升级”。
3. GitHub Actions 继续跑单元测试和 Debug 构建；以后如需云端正式发布，必须把 JKS/密码作为 GitHub Secrets，并保留项目文件夹内离线交接副本，二者不能互相替代。
4. 建立 `release-checklist.md`：版本号、文档加密、单元测试、APK 签名、更新说明、归档、GitHub 上传逐项勾选。

验收：任何接手人仅按照清单即可发布下一版本，且不会换签名、漏文档或上传错误 APK。

## 二、P1 产品重构：把复杂能力放回正确的使用时机

### 2.1 主导航改为“录入、核对、导出”，低频工具下沉

当前能力丰富但入口密集。建议保留采样点、物种、助手、导出四个主入口，同时用顶部工作会话栏把主路径串联；数据库、思维导图、AI 缓存、导入模板、日志、运营中心收进“高级工具”。

不要删除低频能力。先减少它们在首次录入时的视觉竞争，再通过本地匿名使用次数（仅设备内计数，可清除）判断是否保留快捷入口。

### 2.2 图片识别应是“待确认任务”，不是直接录入入口

继续完成既定图片任务队列：每张图状态为排队、压缩、识别、解析、冲突待确认、已应用/失败。多图同一“点位 + 物种”计数冲突必须让用户选择相加、取最大或覆盖；低置信度和未解析行不能自动写库。

图片页要显示实际服务、模型、调用次数、预计费用和失败动作。这样现场人员能快速决定重试、跳过还是手工录入，而不是猜测 AI 有没有成功。

### 2.3 助手拆成“快捷动作”和“审阅结果”两层

全局助手只做短指令、语音、状态入口；助手页用于长结果、数据核对、报告和 AI 过程追溯。两者使用同一个任务中心和结果记录，避免同一请求在两个页面各自显示忙碌/失败状态。

对于会写数据的建议，统一进入动作预览：原文、解析目标、拟议修改、置信度、影响条目数、撤销能力。AI 永远不直接覆盖现场数据。

## 三、P1 性能与可靠性：针对 90/120Hz 和大数据，而不是只削弱视觉效果

1. 建立性能基准数据：100 点位 × 500 物种、50 张图片批次、20 个历史数据集。记录启动、首帧、滚动、点位切换、导出准备、内存峰值和掉帧。
2. 列表和统计只订阅可见点位/可见物种的摘要；完整 Dataset 变换、导出、图片压缩、AI 解析均在后台调度。避免一次计数就复制/序列化整个 Dataset。
3. 高刷新率模式按实际 `Display.Mode` 与帧时间验证 60/90/120Hz；设置页显示当前实际刷新率和“系统未接受锁帧”的原因，不再只提供没有证据的开关。
4. 每个高成本 UI（模糊、动画、预览大表、长日志）都有滚动/低性能设备降级策略，但优先修复主线程工作、重复重组和大对象分配，而不是简单关效果。
5. 给数据集 JSON 的解码失败、Room 迁移、导出模板、备份导入建立黄金样本与升级回归测试。

## 四、P2 数据质量：让错误更早出现、更容易修复

1. 在录入时显示“缺湿重、分类不完整、异常负值、疑似重复物种、点位体积异常”数量，但不阻断现场录入。
2. 导出前体检分成阻断、需确认、提示三级；每条有“定位到条目/忽略一次/批量修复”的明确动作。
3. 物种名称采用本机别名、分类、湿重的匹配解释卡：告诉用户匹配到了哪个来源、为何采用该值、如何撤销。
4. 对有修改风险的批量指令和导入建立审计记录：来源、时间、影响数量、前后摘要和撤销快照。

## 五、P2 工程结构：优先稳定边界，不急于拆 Gradle 模块

1. 页面只负责 Compose 装配；数据编辑、图片任务、AI 路由、备份、导出拆到独立控制器和纯领域函数。
2. 继续保留 Dataset JSON 兼容层，先以读写性能数据决定是否迁移为关系表；迁移必须可回滚并覆盖旧样本。
3. 每个高风险路径必须有单元测试：路由、版本比较、备份选择、迁移、导出黄金文件；关键 Compose 流程做语义树测试，真机测试由人工验收。
4. 删除或隐藏重复的 API1/API2 表单、重复任务状态、旧的自动冲突合并逻辑；兼容层只保留在数据迁移和内部适配器，不再作为产品概念。

## 六、推荐路线图

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| 7.0 稳定性 | 工作会话栏、迁移校验、更新发布门禁、性能基准 | 不丢数据、可定位卡顿、可持续发布 |
| 7.1 现场效率 | 图片任务队列、动作预览、导出前体检 | 少返工、AI 不误写 |
| 7.2 规模化 | 大数据索引/分页、性能回归、审计记录 | 100×500 基准稳定 |
| 7.3 可选扩展 | 付费/授权、云同步、团队协作 | 在本地流程稳定后再评估 |

## 七、不建议现在做的事

- 不要为了“模块化”立刻拆成多 Gradle module；当前收益小于构建和依赖维护成本。
- 不要增加更多 AI 入口或固定模型名；先让已有任务的来源、失败、确认和撤销清楚。
- 不要把 GitHub Debug 包当成正式更新通道；正式签名迁移完成后再把自动更新作为默认路径。
- 不要在没有真实使用数据前删掉离线语音、思维导图、导出等低频能力；先下沉入口并观察现场流程。
